# 第7章 App Lab 综合验证：从部署预检到运行复盘

## 学习目标

完成本章后，读者应能够：

1. 将一次部署定义为有目标、版本、时间窗口、负责人和 `run_id` 的运行批次。
2. 按项目声明、目标能力、运行配置、受控启动、健康观察、功能与物理结果、故障处置、交接八个门逐层推进。
3. 为每个门登记证据来源和结论等级，遇到缺失、过期或冲突时停止推进，而不是推测通过。
4. 将模拟演练、设备只读观察、受控操作和独立验证分开记录。
5. 使用可复用的交接模板留下回退条件、未决问题和下一位操作者需要的事实。
6. 判断“第五篇正文范围完成”与“UNO Q 现场验收完成”之间的差距。

## 背景与边界

Arduino UNO Q 的 App 将 Linux 侧 Python、可选的 MCU Sketch 和 Brick/容器组织在一个项目中；`app.yaml` 是声明入口，而不是部署成功凭证。[Arduino App specification](https://github.com/arduino/arduino-app-cli/blob/main/docs/app-specification.md) Arduino 的 [App Lab 示例教程](https://docs.arduino.cc/software/app-lab/tutorials/examples/)介绍了选择示例、点击 Run、等待启动并交互的基本流程。UNO Q 数据表同时指出，应用启动后仍可能有运行时错误，App Lab Console 的 Start-up、Main (Python) 和 Sketch (Microcontroller) 输出承担不同观察任务。[Arduino UNO Q datasheet](https://docs.arduino.cc/resources/datasheets/ABX00162-datasheet.pdf)

前六章已建立项目结构、生命周期、依赖预检、配置分层、日志证据包和健康处置方法。本章要回答的是：怎样把这些方法组织成**一次可复核的部署验证与交接**。下述门禁、`run_id`、证据等级和交接模板是本书的工程建议，不是 App Lab 官方内置状态机或一键导出能力。

本仓库没有本次任务的目标 UNO Q 连接、现场授权、已核验的目标镜像、物理回读和回滚窗口。本章只写可执行的现场步骤与离线演练材料；不会实际点击 Run、上传 Sketch、安装 Brick、修改配置、重启服务或操作硬件。保持 `draft`，不宣称部署或验收完成。

## 1. 从“点 Run”转为“运行批次”

一次运行批次至少要绑定以下身份：

| 字段 | 记录内容 | 作用 |
| --- | --- | --- |
| `batch_id` / `run_id` | 交接批次与单次运行的唯一标识 | 防止多次尝试的日志、快照和结果混用 |
| 目标别名 | 非敏感的设备标识、连接方式和现场位置 | 防止将观察结果归错设备；不公开序列号 |
| App 版本 | 代码提交号、`app.yaml` 版本与依赖清单 | 复现实际运行内容 |
| 运行环境 | 目标系统镜像、App Lab/CLI 的实际版本或 `UNKNOWN` | 防止把文档默认值写成设备事实 |
| 配置身份 | 第五篇第4章的脱敏快照指纹 | 关联部署与日志，但不证明 Secret 正确 |
| 时间与时钟 | 开始/结束时间、时区、时钟来源和偏差 | 判断日志窗口与信号新鲜度 |
| 人员与边界 | 操作者、复核者、授权范围、安全停机与回退负责人 | 确定谁能进入受控动作 |

同一个 `run_id` 下的证据必须能回到相同目标、版本和配置。更改 App、配置或目标后要创建新运行；一次失败后再点击 Run 也要创建新的 `run_id`。旧运行的 `PASS` 不会自动继承。字段未知时写 `UNKNOWN`，不留空让后续读者误判为“不适用”。

在本章配套的离线演练中，前几章的示例各自使用不同运行 ID：配置快照是 `run-042`，日志关联是 `run-043`，健康样例是 `run-044`/`run-045`。它们只能作为**分项规则演练**，绝不可拼成一份“同次部署成功”的证据包。

## 2. 八个门：阶段、证据与停止条件

| 门 | 必须回答的问题 | 最低交付物 | 未满足时 |
| --- | --- | --- | --- |
| G0 范围与安全 | 哪台设备、哪个 App、谁授权、怎样停机与回退？ | 批次说明、操作者、权限、风险和回退负责人 | `BLOCKED`；不进入受控动作 |
| G1 项目契约 | `app.yaml`、Python 入口、可选 Sketch/Brick 是否符合预期？ | 版本固定的目录/声明检查、依赖清单 | `BLOCKED` 或 `UNKNOWN`；修正项目 |
| G2 目标与配置 | 目标能力、端口、模型、配置指纹和 Secret 注入是否可核对？ | 目标只读能力快照、脱敏配置、冲突清单 | `UNKNOWN` 时不猜测“可部署” |
| G3 受控启动 | 经授权的 Run 是否完成；启动日志属于本次运行？ | Start-up 原文、代码/配置身份、操作者与时间 | 启动失败则停止；不读旧日志补结论 |
| G4 运行健康 | Python、Sketch、Brick 等**实际必需**信号是否新鲜？ | Main/Sketch 原文、规范化事件、健康快照 | 故障或 `UNKNOWN` 时按第6章处置 |
| G5 功能与结果 | 安全功能检查是否有请求/结果关联和独立状态证据？ | 请求 ID、回执、状态回读、必要的人工确认 | 不把启动或心跳当成物理结果 |
| G6 异常与恢复 | 失败、超时或回退后能否判定目标状态？ | 故障记录、未决请求对账、恢复/回退验证 | `UNKNOWN` 时冻结重试与交接宣称 |
| G7 脱敏交接 | 其他人能否用证据复核结论和缺口？ | 文件清单、校验值、结论等级、未决项、责任人 | 缺必要证据则保持开放 |

G0～G2 可以在开发机上先完成**文档/静态预检**，但目标能力、版本、端口占用和权限还需在实际目标上只读核对。G3～G6 涉及设备运行或现场观察，不能由离线模拟代替。G7 可以交接一个“不通过/待验证”的包，但包内不能把未完成的门写成通过。

建议统一使用五种记录状态：`NOT_RUN`（未执行）、`SIMULATED`（仅本地替身）、`OBSERVED`（目标上的只读事实）、`VERIFIED`（满足该门的独立证据和复核）、`BLOCKED/UNKNOWN`（已知前置不满足/结果不可判定）。`VERIFIED` 必须附带**验证范围**；例如“在某版本、某时间窗口、某只读功能路径下通过”，不能写成无条件“设备完全安全”。

### 2.1 门与门之间不自动传递结论

- G1 的 `VALID` 只说明声明形状，不能代替 G2 的目标能力。
- G2 的 `READY` 若来自人工模拟能力清单，只是模型输出；不能代替目标设备预检。
- G3 的“启动完成”不能代替 G4 的运行健康。
- G4 的 `HEALTHY_OBSERVED` 不能代替 G5 的业务或物理结果。
- G5 的一次成功不能代替 G6 的故障/回退能力，更不能代替长时间稳定性、性能和安全验收。

任何门发现身份冲突、时钟不可用、证据来源不明或可能已执行却无结果的请求，都应转入 `UNKNOWN` 路径。原因查清之前，不自动重试或发布“通过”结论。

## 4. 现场运行手册：逐门推进

### 4.1 开始前：只读盘点与安全准备

1. G0：明确目标别名、App 版本、工作窗口、执行与复核人员、网络/物理影响、应急停机和回退负责人。控制类项目必须先确认现场允许的安全状态。
2. G1：依据[第五篇第1章](./第1章_App_Lab开发基础_应用结构与验证边界.md)检查项目文件；依据[第五篇第3章](./第3章_AppLab启动配置与Brick依赖_从声明到可部署性检查.md)检查 `app.yaml`、Brick/模型/设备与端口声明。静态检查结果只写“声明预检”。
3. G2：在目标设备上**只读**核对镜像、App Lab/CLI 版本、可用依赖和端口占用；对照[第五篇第4章](./第4章_AppLab配置分层与多环境运行参数_从开发机到现场板.md)生成的脱敏配置快照。Secret 不进入仓库、Console 截图或交接附件。
4. 若目标身份不明、声明/目标冲突、回退不可执行、人员授权缺失或时间窗口不安全，停止在 G2。记录阻断原因和重新评审条件。

### 4.2 受控运行：一次 Run，一份新证据包

只有 G0～G2 的目标现场核对和授权都满足时，才可以由现场操作者进入 G3。为本次运行创建唯一 `run_id`，记录 App/配置身份，按官方 App Lab 流程启动；若是内置示例，需要先复制才能编辑。[Arduino App Lab examples](https://docs.arduino.cc/software/app-lab/tutorials/examples/) 不在本仓库脚本中自动调用 Run。

G3 分别保存 Start-up 原文；G4 分别保存 Main (Python) 与 Sketch (Microcontroller) 原文。按[第五篇第5章](./第5章_AppLab运行证据包与日志关联_从run_id到可检索证据.md)建立规范化索引，隔离旧运行、未关联和指纹冲突事件。按[第五篇第6章](./第6章_AppLab健康观察与故障处置_从信号到安全恢复.md)检查持续信号的身份、新鲜度与必需/可选边界。组件没有使用时写“不适用”，不可用时写“未观察”，不要制造空日志当作成功证据。

G5 选一个**预先批准的只读或安全功能**，记录请求 ID、参数摘要、响应和独立状态来源。如果项目有执行器，未经现场安全评估不得把演示命令直接用于物理动作。Bridge/RPC 超时或重连时，按[第四篇第4章](../第4篇_PythonBridge/第4章_Python_Bridge结果账本与状态查询_从返回值到可验证证据.md)先查结果账本或独立状态，不盲目重发。

G6 记录至少一个**预先定义**的异常处置与回退条件，但故障注入不是本章必须在线执行的动作。没有安全实验窗口时，只做桌面推演，并把实际故障/回退验证写成 `NOT_RUN`。发生真实故障时先保全证据，按第6章人工恢复门处置；一次重启既不是原请求撤销证明，也不是回滚成功证明。

### 4.3 交接：结论与缺口同等重要

G7 使用[复盘与交接模板](../../code/第5篇_AppLab/第7章_AppLab综合验证_从部署预检到运行复盘/handoff-template.md)记录八个门的状态、证据引用、版本、回退条件和未决问题。可以交接 `BLOCKED` 或 `UNKNOWN`，只要下一位操作者知道停止点和责任人；不能为了“交接完成”修改事实。交付前按第五篇第5章的规则审阅、脱敏、限定访问，再为**交付副本**记录文件大小和 SHA-256。哈希不证明来源真实或设备安全。

## 5. 离线演练：复核分项规则，识别无法拼接的证据

本练习运行四个已有脚本：声明预检、配置快照、日志关联和健康分类。它们使用不同的内置样例，输出是 `SIMULATED` 或 `LOCAL_MODEL`；演练目标是识别各自可证明的命题及**不可跨运行合并**的边界。

代码说明
- 用途：把前几章的离线分项实验按部署顺序复跑，并记录每项的证据等级。
- 运行环境：Python 3.10 或更高版本；Windows、Linux 或 macOS。
- 文件位置：第五篇第3～6章各自 `code/` 目录；本章[配套说明](../../code/第5篇_AppLab/第7章_AppLab综合验证_从部署预检到运行复盘/README.md)汇总入口。
- 依赖：Python 标准库与仓库内固定模拟输入；不需要网络、App Lab 或板卡。
- 操作步骤：在仓库根目录顺序执行下列只读命令；不要把 `run-042`、`run-043` 和 `run-044` 的结果填成一个批次的通过证据。脚本不写文件、不控制设备；涉及真实部署时必须另按第4节授权与停止条件执行。
- 预期输出：声明示例包含 `VALID` 及负例；快照示例显示 `run-042`；日志示例显示 `run-043` 的 `RUNTIME_ERROR`；健康示例显示 `run-044` 的 `UNKNOWN`。
- 故障排查：确认从仓库根目录运行、Python 可执行、样例文件在原位；若输出与本章不符，先核对样例和脚本版本，不用设备结果“补齐”离线结论。
- 验证方式：逐条核对命令的退出码与样例输出，再在[示例复盘记录](../../code/第5篇_AppLab/第7章_AppLab综合验证_从部署预检到运行复盘/sample-handoff.md)中观察为什么各运行不能合并；这不构成目标板部署验收。

~~~text
python -B "code/第5篇_AppLab/第3章_AppLab启动配置与Brick依赖/deployment_contract.py"
python -B "code/第5篇_AppLab/第4章_AppLab配置分层与多环境运行参数/run_config_snapshot.py"
python -B "code/第5篇_AppLab/第5章_AppLab运行证据包与日志关联/correlate_events.py" --metadata "code/第5篇_AppLab/第5章_AppLab运行证据包与日志关联/sample_run.json" --events "code/第5篇_AppLab/第5章_AppLab运行证据包与日志关联/sample_events.jsonl"
python -B "code/第5篇_AppLab/第6章_AppLab健康观察与故障处置/evaluate_health.py" --snapshot "code/第5篇_AppLab/第6章_AppLab健康观察与故障处置/sample_stale.json"
~~~

输出要点（固定模拟输入；仅是本地规则演练）：

~~~text
SIMULATED manifest=VALID ports=5000 bricks=arduino:dbstorage,arduino:objectdetection
SIMULATED snapshot=run-042 env=staging redacted=DB_PASSWORD
SIMULATED run_id=run-043 total=6 correlated=3 stale=1 uncorrelated=1 fingerprint_conflict=1
SIMULATED verdict=RUNTIME_ERROR errors=1 warnings=0 sources=main-python,startup
{"action": "HOLD_AND_RECONCILE", "checks": {"brick.camera": "PASS", "mcu.status": "UNKNOWN_STALE", "python.loop": "PASS"}, "health": "UNKNOWN", "run_id": "run-044", "scope": "LOCAL_MODEL"}
~~~

输出节选并非四条命令的全部输出。`VALID`/`READY`、`RUNTIME_ERROR` 和 `UNKNOWN` 各自属于原章的教学模型，不能解释为 App Lab 原生返回。尤其不能用 `run-042` 的配置快照为 `run-043` 的日志提供配置身份；更不能用 `run-044` 的健康快照证明 `run-043` 已恢复。

## 6. 交接包：结构、示例与评审

建议每个真实 `run_id` 拥有独立的受限目录；下列结构是推荐清单，不是 App Lab 自动创建的文件：

~~~text
handoff/
└── <run_id>/
    ├── handoff.md               # 八个门的状态、结论、未决项与责任人
    ├── run.json                 # 目标别名、版本、时间和运行身份
    ├── config.redacted.json     # 脱敏配置快照；无 Secret
    ├── logs/                    # 分来源保存的、经审阅的日志副本
    ├── events.jsonl             # 规范化事件及原文引用
    ├── health.json              # 检查范围、时间和证据引用
    ├── outcomes.md              # 安全功能、独立状态和异常路径
    └── manifest.json            # 交付副本清单与校验值
~~~

不存在的证据文件**不应创建空文件冒充采集**；在 `handoff.md` 写明 `NOT_RUN`、`UNAVAILABLE` 或 `UNKNOWN` 及原因。公开发布前去除凭据、个人信息、序列号和业务敏感数据；未经审阅的原始日志只能在获准的受限位置保存。示例文件[`sample-handoff.md`](../../code/第5篇_AppLab/第7章_AppLab综合验证_从部署预检到运行复盘/sample-handoff.md)故意保持阻断状态，示范没有设备证据时如何准确复盘并交接。

评审至少由操作者与另一名复核者核对：运行身份是否一致，门的状态是否有证据，缺口是否明确，回退条件是否可执行，是否误把模拟结果升级为现场结论。后续补证据要保留版本和时间线，不原地覆盖已交付的证据副本。

## 8. 常见问题

### Q1：离线四个脚本都运行成功，能否标记 G0～G4 通过？

不能。它们属于不同的模拟运行，各自只验证局部规则；没有目标身份、实际版本、目标能力或 App Lab 运行证据。

### Q2：G7 已填完整，是否意味着部署通过？

不意味着。G7 可以完整记录阻断、未知和未执行；“交接可读”与“系统已验收”是两种结论。

### Q3：必须做故障注入才能结束本篇吗？

不必为完成教材正文而对真实设备注入故障。现场是否实施取决于风险评估、受控窗口和授权；没做就写 `NOT_RUN`，不能借桌面推演代替验证。

### Q4：何时可以进入第六篇 OpenCV？

作为学习路线，可以在掌握本篇项目与证据边界后继续[第六篇 OpenCV](../第6篇_OpenCV/README.md)。如果要把视觉结果连接到物理动作，仍须先满足本篇的现场安全、结果闭环和交接要求。

## 9. 本章小结与下一篇

一次可信的 App Lab 部署验证需要同一运行批次的身份、前置条件、日志、健康、功能/物理结果、异常对账和脱敏交接。任何一个关键门缺失，都应明确阻断或未知，而不是靠别次演练补齐。

第五篇第1～7章的**正文范围至此收束**，后续更新以勘误、来源核验、图示渲染和现场证据补充为主；目前不预设第8章。下一篇从[摄像头输入与 OpenCV 管线](../第6篇_OpenCV/README.md)展开。完整书稿状态与证据边界仍以[项目首页](../../README.md)为准。
