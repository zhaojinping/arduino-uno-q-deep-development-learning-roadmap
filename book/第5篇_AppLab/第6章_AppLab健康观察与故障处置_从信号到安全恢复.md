# 第6章 App Lab 健康观察与故障处置：从信号到安全恢复

## 学习目标

读完本章后，读者应能够：

1. 区分进程存活、依赖就绪、功能可用与物理结果四种不同层级的健康命题。
2. 为一次运行定义需要持续观察的信号、有效期、运行身份和证据来源。
3. 对当前故障、陈旧信号、身份冲突、未观测信号和可降级能力分别作出保守判定。
4. 依照“先保全现场、再对账、后恢复”的顺序处理故障，避免把重启当作业务结果确认。
5. 使用离线模拟脚本复核一组健康快照，同时正确描述脚本的验证边界。

## 背景与边界

在 Arduino UNO Q 上，一个 App 可以组合 Linux 侧 Python、可选的微控制器 Sketch 与 Brick。官方 App 规范描述了双侧职责及其基于 RPC 的通信。[Arduino App specification](https://github.com/arduino/arduino-app-cli/blob/main/docs/app-specification.md) UNO Q 数据表说明，App Lab Console 的 Start-up、Main (Python)、Sketch (Microcontroller) 标签提供不同输出；应用能够启动成功，却仍可能在运行时出错。[Arduino UNO Q datasheet](https://docs.arduino.cc/resources/datasheets/ABX00162-datasheet.pdf)

因此，“App Lab 显示已启动”只是一个入口事实，不等于依赖、功能和硬件都健康。本章在[第五篇第2章](./第2章_AppLab运行生命周期_导入启动运行与停止.md)的生命周期、[第五篇第5章](./第5章_AppLab运行证据包与日志关联_从run_id到可检索证据.md)的证据包之上，增加一层**本书建议的健康判定与处置策略**。下面的 `HEALTHY_OBSERVED`、`DEGRADED`、`FAULT_OBSERVED`、`UNKNOWN` 不是 App Lab 官方状态、内置探针或设备安全认证。

本章所有数值阈值和示例信号都是教学假设。离线脚本只读取仓库内模拟 JSON，不连接 App Lab、Arduino App CLI、Router/Bridge、MCU 或真实传感器；它不会控制设备、重启进程或改变配置。凡涉及现场执行，必须先确认设备特性、受控模式、人员职责和恢复条件。

## 1. “在运行”不等于“可安全工作”

健康观察至少分为四层，后一层不能由前一层自动推出：

| 层级 | 典型观察 | 能回答的问题 | 仍不能回答的问题 |
| --- | --- | --- | --- |
| 存活 `liveness` | App/进程仍在运行、心跳持续 | 主循环或进程是否仍可被观察 | 依赖是否可用、请求能否成功 |
| 就绪 `readiness` | 所需 Brick、连接和配置检查通过 | 这次运行所需资源是否可进入工作状态 | 代表性业务操作是否成功 |
| 功能检查 `functional check` | 有请求 ID 的只读或安全测试得到预期回执 | 这条功能路径是否在受控条件下工作 | 实际执行器或外部系统是否达成目标 |
| 物理或业务结果 | MCU 状态回读、独立传感器、人工验收记录 | 目标状态是否得到可复核的证据 | 所有环境、负载和故障条件下都可靠 |

例如，Python 心跳正常而 MCU 状态回读过期，只能说 Linux 侧仍有新鲜输出；不能从“心跳正常”推断外设安全。Sketch 串口打印了命令编号，也只说明 Sketch 输出了这段文字；最终状态仍需独立回读或业务结果闭环。第四篇第4章的[结果账本与状态查询](../第4篇_PythonBridge/第4章_Python_Bridge结果账本与状态查询_从返回值到可验证证据.md)给出了请求级 `UNKNOWN` 的处理模型，本章把同样的审慎原则用于运行健康。

对没有 Sketch 或 Brick 的 App，不应伪造相应的“成功”探针。启动前按 `app.yaml` 和实际设计登记**必需检查**与**可选检查**，并说明检查本身的采集方法；未配置的组件标注“不适用”，而不是“通过”。

## 2. 设计一次运行的健康观察契约

建议在运行前确定以下字段，并写入第五篇第5章的运行证据包：

| 字段 | 作用 | 缺失或冲突时 |
| --- | --- | --- |
| `run_id`、脱敏 `config_fingerprint` | 绑定本次运行和配置身份 | 不跨运行拼接；进入 `UNKNOWN`，先对账 |
| `observed_at_utc`、检查 `ts_utc` | 计算新鲜度 | 时钟来源不可靠时不使用自动有效期结论 |
| `required_checks` | 必须新鲜且通过的检查名 | 缺一项仍是 `UNKNOWN`，不是成功 |
| `optional_checks` | 失败后可能允许人工评估降级的能力 | 可标 `DEGRADED`，但不能自动切换工作模式 |
| `status`、`evidence_ref` | 记录 `PASS`/`FAIL`/`UNKNOWN` 及证据位置 | 没有可追溯来源时不得升级为“已验证” |
| `max_age_seconds` | 本地策略允许的最长信号年龄 | 只适用于持续信号，不应用于一次性的历史启动日志 |

选择有效期时，先看信号产生周期、采集延迟、时钟误差和业务风险。例如，教学样例把上限设为 30 秒，这**不是** App Lab、UNO Q、Bridge 或 MCU 的官方指标，也不适用于所有现场。时钟若不同步，先记“时序未知”，不要因一个墙上时钟读数就恢复输出。需要更严谨的超时设计，可结合[第三篇第3章](../第3篇_Linux/第3章_Linux可观测性与资源管理_日志时间与安全回滚.md)的时间来源和[第三篇第6章](../第3篇_Linux/第6章_Linux与Python_Bridge现场测试与性能治理_从基准压测到故障注入.md)的现场基准。

每条观察至少写清楚：由谁产生、何时产生、属于哪次运行、是否为必需、证据在哪里、失联时怎样转入安全状态。`run_id` 不符、指纹不符、过期、未来时间、缺失和状态本身为 `UNKNOWN` 都是不同的诊断线索，不能统统折叠成“失败一次”。

### 2.1 判定顺序

本章建议先评估输入质量，再评估状态值。下表中的“动作”是**人工处置建议**，不是脚本执行的控制命令。

| 条件 | 本地模型结论 | 操作方向 |
| --- | --- | --- |
| 有**当前且身份匹配**的必需检查 `FAIL` | `FAULT_OBSERVED` | 暂停相关输出、保留现场并诊断；未知的其他检查照样列出 |
| 没有上述故障，但必需检查缺失、过期、身份冲突或 `UNKNOWN` | `UNKNOWN` | 冻结不可逆操作；查运行身份、时间和独立状态 |
| 必需检查都新鲜通过，但可选检查不通过或不可信 | `DEGRADED` | 仅由操作者评估是否有预先批准的降级模式 |
| 所有声明的检查都新鲜、身份一致且通过 | `HEALTHY_OBSERVED` | 继续观察；仍不能替代功能或物理验收 |

这个优先级保留已确认的故障：即使另一路信号还未知，也不把已观察到的必需故障冲淡为“全局仅未知”。反过来，缺失信号绝不能被猜成 `PASS`。一次异常不应自动循环重启；确认起动、停止、重试及对账条件是独立决策。

## 4. 故障处置：先界定风险，再找根因

### 4.1 发现异常的前五分钟

1. **先约束输出**：若 App 涉及电机、继电器、加热或其他可能有危险的动作，按现场预案确认安全状态和人工接管方式；软件界面“停止”不自动证明物理输出已安全。
2. **固定现场**：记录当前 `run_id`、配置指纹、时间来源、版本、操作者和现象。按第五篇第5章分别保存 Start-up、Main (Python)、Sketch 输出，保留原文；敏感内容先限制访问。
3. **识别故障层**：启动/编译失败、Python 运行时错误、Brick 未就绪、Bridge/RPC 超时、MCU 状态未知、外设反馈不一致，分别定位。日志报错是线索，不必然是根因。
4. **查询独立状态**：对可能已发送的请求，查第四篇第4章的结果账本和目标状态。通信超时可能意味着请求仍在执行，不能直接重发。
5. **决定是否恢复**：只有操作者确认风险受控、故障范围明确、恢复条件具备，才进入下一节。否则维持 `UNKNOWN` 或 `FAULT_OBSERVED` 并移交。

| 场景 | 先看什么 | 暂不做什么 |
| --- | --- | --- |
| Sketch 编译错误 | Start-up 原文、代码版本、依赖与板卡目标 | 不以旧 Sketch 输出声称本次启动成功 |
| Python 异常而启动完成 | Main (Python)、请求 ID、异常前后日志 | 不用“启动成功”覆盖运行时故障 |
| Brick 不可用 | 声明、目标能力快照和 Brick 自身状态 | 未证明降级安全前，不绕过依赖强行运行 |
| Bridge 超时或 MCU 无回执 | 连接代次、结果账本、MCU 独立状态 | 不盲目重发可能已执行的动作 |
| 日志时间或身份冲突 | 采集时间、`run_id`、配置指纹、设备别名 | 不仅凭时间相近拼接为同一次运行 |

### 4.2 恢复门与退出条件

恢复不是“按一次 Run”。至少完成：故障影响范围界定；受控输出或人工接管确认；当前配置和目标设备身份复核；未决请求对账；必要数据和原日志保全；恢复方案、回退条件和负责人记录。若涉及硬件，先在安全条件下核对物理状态。

恢复时生成**新的** `run_id`，明确它与故障运行的关系；不得把旧运行的日志、健康快照或指纹复制成新运行的通过证据。按启动、依赖、只读或安全功能、必要的物理回读逐层复测。任何一层再次进入 `UNKNOWN` 或 `FAULT_OBSERVED`，立即停止向下推进并按预案回退。重启可能清除症状，也可能重复未完成请求，因此必须以独立状态查询和结果账本闭环。

## 5. 实验：离线评估健康快照

下面的脚本把教学快照分成必需和可选检查，先核对运行身份与时间，再得出本地判定。两份输入分别演示“MCU 信号过期”和“Python 必需检查明确失败”。`evidence_ref` 在样例中以 `simulation:` 开头，仅是模拟标记，不是设备原始证据。

代码说明
- 用途：演示对必需/可选健康信号进行新鲜度、身份和状态判定。
- 运行环境：Python 3.10 或更高版本；Windows、Linux 或 macOS。
- 文件位置：`code/第5篇_AppLab/第6章_AppLab健康观察与故障处置/evaluate_health.py`，样例在同目录。
- 依赖：Python 标准库；不需要板卡、网络、App Lab 或额外包。
- 操作步骤：从仓库根目录分别对两份模拟快照执行下列只读命令；脚本不写文件、不发送请求、不切换输出。现场出现异常时，先遵循第4节安全步骤。
- 预期输出：过期样例为 `UNKNOWN`/`HOLD_AND_RECONCILE`；当前必需故障样例为 `FAULT_OBSERVED`/`HOLD_AND_DIAGNOSE`。
- 故障排查：检查输入是否为 JSON 对象、时间是否使用 UTC、指纹是否为 64 位小写十六进制、检查名是否重复、时间差是否超过本例 30 秒；输入错误不会被当成“健康”。
- 验证方式：对照输出中每项检查的分类；这只验证本地模型和固定模拟数据，不构成 App Lab、MCU 或物理安全验证。

~~~text
python -B "code/第5篇_AppLab/第6章_AppLab健康观察与故障处置/evaluate_health.py" --snapshot "code/第5篇_AppLab/第6章_AppLab健康观察与故障处置/sample_stale.json"
python -B "code/第5篇_AppLab/第6章_AppLab健康观察与故障处置/evaluate_health.py" --snapshot "code/第5篇_AppLab/第6章_AppLab健康观察与故障处置/sample_fault.json"
~~~

示例输出（`LOCAL_MODEL`；仅使用模拟输入）：

~~~json
{"action": "HOLD_AND_RECONCILE", "checks": {"brick.camera": "PASS", "mcu.status": "UNKNOWN_STALE", "python.loop": "PASS"}, "health": "UNKNOWN", "run_id": "run-044", "scope": "LOCAL_MODEL"}
{"action": "HOLD_AND_DIAGNOSE", "checks": {"brick.camera": "PASS", "mcu.status": "PASS", "python.loop": "FAIL"}, "health": "FAULT_OBSERVED", "run_id": "run-045", "scope": "LOCAL_MODEL"}
~~~

第一条里，陈旧的 `mcu.status` 并不说明 MCU 已经失败，只说明**当前没有足够新鲜的状态证据**。第二条里，当前 `python.loop` 明确失败；“故障已观察到”仍不是根因诊断。脚本输出的动作字段只是给人的建议标签，没有控制逻辑。

## 7. 常见问题

### Q1：进程和 Python 心跳都正常，可以自动恢复设备动作吗？

不可以。它们只覆盖存活层；依赖、请求结果和物理状态仍需分别核对。自动恢复若可能重放动作，必须另有经验证的安全与幂等设计。

### Q2：一个必需检查失败，另一个检查过期，为什么结论是 `FAULT_OBSERVED`？

因为已有身份匹配且新鲜的必需失败证据。过期项仍显示为 `UNKNOWN_STALE`，故障原因与整体状态没有被宣称“已全部查清”。

### Q3：`HEALTHY_OBSERVED` 是否等于通过验收？

不等于。它只表示**本次快照所声明**的检查在本地规则下新鲜且通过；还缺真实来源验证、目标镜像和负载测试、物理回读及项目验收标准。

### Q4：为什么不直接自动重启？

重启会改变现场并可能掩盖未决请求。对于可能已发送的动作，先通过独立状态和结果账本确认，否则重试可能造成重复执行。

## 8. 本章小结与下一步

本章建立的核心顺序是：明确检查范围，核对运行身份与新鲜度，按必需/可选信号作保守判定，保全证据并经过人工恢复门。它是运行治理模型，不是 Arduino App Lab 的内置健康 API，也不是硬件安全证明。

第五篇还需要一个篇末综合验证：把项目声明、目标能力、运行配置、启动日志、健康快照、故障对账和交接材料串成一次可复核的部署演练。这将是[第五篇第7章（规划中）](./README.md#后续规划)，完成后本篇正文范围即可收束；目前不预设第8章。即使正文收束，各章仍须保持 `draft`，直到目标板实测与图示/出版复核满足发布条件。
