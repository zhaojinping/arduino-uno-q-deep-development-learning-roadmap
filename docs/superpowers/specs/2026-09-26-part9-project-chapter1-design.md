# 第九篇第1章：实验室环境监测与告警设计

## 设计目标

以“实验室环境监测与告警”为第九篇贯穿项目的场景，编写第一章《项目立项与需求基线：从场景到可验收目标》。章节面向已经学习前八篇的读者，先把场景、利益相关者、需求、验收标准和证据边界写清楚，为后续架构与实现章节提供可追溯的输入。

项目只负责观察、记录和告警，不自动驱动继电器、电机、门锁、加热器或其他执行器。具体传感器型号、接线、采样周期和部署拓扑不在本章臆定；须在后续架构/实现章节中，结合官方资料、实际可用硬件与风险约束后确定。

## 已确认的设计选择

- 贯穿项目：实验室环境监测与告警。
- 核心安全边界：监测与通知，不自动控制物理执行器。
- 第一章职责：定义项目章程、范围、需求基线、验收矩阵、未决项和证据等级；不提前展开完整实现。
- 数据证据：章节示例和自动化测试先使用明确标记的合成数据。只有后续经批准的现场验证才可标记为真实传感器观察。
- 平台：以 Arduino UNO Q 为目标学习平台，但不得暗示开发板本身包含尚未确认的环境传感器。

## 场景与概念数据流

场景关注实验室或设备间环境读数、设备/采集链路健康状态，以及可解释的阈值告警。逻辑链路为：数据源（合成或后续经确认的传感器）→ 采集适配 → 单位/时间/来源校验 → 本地状态与事件记录 → 规则告警和可视化 → 可选的远程遥测。

本设计不指定采集适配器必须运行在 MCU 或 Linux，也不指定远端服务、Broker 或具体传感器；这些是后续架构选择。远程遥测默认关闭，不作为第一章或本地测试的隐含依赖。每条数据都应区分 `SYNTHETIC`、`OBSERVED` 等来源状态，避免把模拟结果包装成实测。

## 本章范围

本章应包含：

1. 项目背景、目标读者、利益相关者和典型使用流程。
2. 明确的范围内事项、范围外事项和假设。
3. 功能需求与非功能需求；每项需求具有稳定 ID、可验证的验收条件和验证方法。
4. 一张概念边界/数据流图，区分数据源、处理、告警、可视化与可选远程通道，并标出无执行器控制。
5. 风险、依赖、未决决策和需求变更规则。
6. 从合成数据测试到未来目标环境验证的证据分级，以及转交给下一章系统架构设计的输入清单。

本章不包含可直接连板运行的程序、传感器接线图、未经核实的性能目标、云服务配置或现场安全阈值。示例阈值只用于解释验收方法，必须标注为教学合成值，不能表述成实验室安全规范。

## 验收原则

- 需求表中的每个验收条件可通过文档审查、确定性合成数据测试或经批准的后续硬件验证来检查。
- 合成数据、纸面架构、主机端测试和目标板/传感器观察分开标记；前者不能替代后者。
- 无效、缺失、过期、重复或乱序读数有明确处理结果，不得静默变成正常状态。
- 告警结果包含触发依据和数据来源；无数据、来源不明或状态未知时，不报告为“正常”。
- 本章及其自动化测试不访问网络、不连接 Broker、不访问传感器、不控制执行器，也不授予部署权限。
- 只有在传感器、目标身份、授权范围、验证步骤和原始证据要求已确定后，后续章节才可描述目标环境验证；实际验证仍需单独授权和执行。
