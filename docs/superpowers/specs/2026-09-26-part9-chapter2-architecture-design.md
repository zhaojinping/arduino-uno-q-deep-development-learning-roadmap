# 第九篇第2章《系统架构设计》设计规格

## 目标与读者

本章承接第九篇第1章《项目立项与需求基线》，面向已完成前八篇学习、准备把 Arduino UNO Q 能力用于综合项目的读者。目标是把实验室环境监测与告警需求映射成清晰、可审查、可分阶段验证的系统边界，为后续传感器选型、数据处理、持久化、告警和系统验证章节提供共同接口。

本章将架构标记为教学参考设计，不冒充已批准的现场部署架构，也不把纸面设计或主机端合成测试写成 UNO Q 实测。

## 已获确认的架构方向

采用分层混合候选架构：当最终选择的传感器连接到 STM32U585 管理的常规 MCU 接口时，由 MCU 侧负责采集与初步质量标记；Linux 侧负责本地事件接纳、记录、规则计算、告警状态和本地界面；两侧通过 Arduino 官方支持的 Bridge/RPC 接口交换版本化测量事件。

Arduino 官方用户手册说明 UNO Q 的 Linux/MPU 与 STM32/MCU 双处理器分工、MCU 数字引脚管理及 Bridge/RPC 通信；官方数据表区分 MPU 与 MCU 的电气域。因此本章可以将该双侧边界作为架构依据，但不得据此推断某个尚未选定的传感器、电平、引脚或性能配置必然可用。资料入口：

- [UNO Q 官方用户手册](https://docs.arduino.cc/tutorials/uno-q/user-manual/)，核验日期：2026-09-26；用于双处理器、Bridge/RPC 和 App Lab 的官方平台说明。
- [UNO Q 官方数据表](https://docs.arduino.cc/resources/datasheets/ABX00162-datasheet.pdf)，核验日期：2026-09-26；用于区分 MPU、MCU 及其接口/电气边界。连接具体器件前仍须核对对应接口的原始规格。

## 架构目标与强制边界

- 追踪第1章的 `LEM-FR-*` 与 `LEM-NFR-*` 需求；每条测量、告警和展示状态都能回到来源、时间、质量和规则版本。
- 采集端、Bridge/RPC 传输、本地接纳与持久化、规则/告警、展示各有单一职责和可观察的故障边界。
- 无效、缺失、过期、重复、乱序、来源不明或时钟不可信的数据不能被解释成当前正常状态。
- 系统只监测、记录、告警与展示；没有继电器、电机、门锁、加热器或其他物理执行器控制路径。
- 远程遥测/云端外发默认关闭；本章及离线测试不连接外部服务。
- 所有教学输入标为 `SYNTHETIC`；`OBSERVED` 只用于后续确有传感器原始证据的验证。
- 物理量、传感器型号、接口/引脚、采样周期、量程、校准、陈旧窗口、规则阈值、存储介质、缓存容量及部署参数保持未决，不用猜测值补齐。

## 组件职责

| 组件 | 责任 | 不承担的责任/约束 |
|---|---|---|
| 传感器与 MCU 采集适配 | 在经核实的电气/驱动边界内采样；携带来源、单位、事件标识、测量时间语义和初步质量信息 | 传感器未选定；不得在章节里给出接线或额定范围；不自动控制执行器 |
| STM32U585 / Zephyr | 驱动 MCU 常规接口；执行轻量输入检查与事件封装；在必要时提供可观测的采集健康信号 | 不承担 Linux 文件持久化、云服务、复杂 UI 或未经批准的阈值规则；不得假设 Bridge 回调适合阻塞采集 |
| Arduino Bridge/RPC | 作为 MCU 与 Linux 应用之间的受支持逻辑消息边界，传递版本化请求/事件与响应 | 不将其描述为 exactly-once 传输；不得绕过 API 直接占用 Router 管理的底层设备 |
| Linux 应用层 | 校验消息契约、去重、记录事件、维护当前状态、按已批准规则版本评估、产生可追溯告警并服务本地 UI | 不把最后一次有效值冒充当前值；不默认开放网络遥测；存储技术和 UI 技术仍待后续选型 |
| 本地存储边界 | 保存被接纳的测量/质量事件、告警事件、必要配置版本和审核记录；让恢复/丢失状态可判定 | 具体数据库/文件格式、保留期限、事务策略和容量不在本规格中锁定 |
| 本地界面 | 展示正常（仅有效、足够新鲜且规则已配置时）、告警、等待、未知、数据异常和存储/链路退化，并显示最后有效事件时间 | 状态不得只靠颜色表达；界面不是安全联锁或专业检测设备 |

Arduino App Lab 可作为 Linux Python 应用与 MCU Arduino sketch 的候选开发/运行入口；若实施章节选择该入口，需依据目标板当前官方文档和软件版本核实运行、部署及 Bridge 行为。本规格不假定某个 App Lab 版本或 Brick 已安装。

## 候选方案与取舍

1. **分层混合（本章推荐参考方案）**：常规 MCU 接口侧传感器由 STM32 采集；Linux 处理本地存储、告警规则和界面，经 Bridge/RPC 传递事件。它利用 UNO Q 的双处理器边界，能让采集契约和较高层应用分别测试；代价是需要设计跨边界数据契约、断连/重启与重复处理。
2. **MCU 单体**：采集及有限状态判断全部在 STM32，避免 Linux/Bridge 运行依赖；但本项目所需的本地事件记录、规则版本管理和丰富界面能力受 MCU 资源/实现方式约束，且不便复用 Linux 侧应用能力。
3. **Linux 直连**：当输入设备本身是已确认由 Linux 管理的外设，或目标连接器明确属于 MPU 域时可以评估；它不能被泛化为 Linux 直接操作 UNO 风格标准 I/O 引脚，也不能绕过接口电平和资源归属核验。

本章只将方案 1 作为学习项目参考，不封闭将来因传感器/连接器证据而改变选择的可能。方案改变需记录架构决策及其需求、风险和验证影响。

## 数据与事件契约

正文说明测量记录至少包含：`schema_version`、`device_id`、`source_id`、`event_id`、`event_time`（来源时间不可信时不得伪造）、Linux `received_at`、数值、显式单位、`quality`、`quality_reason` 和 `provenance`。记录必须保留测量时间与接收时间的区别；时间不能可信时进入未知/诊断路径。重复去重依赖稳定事件标识，但该标识的生成、跨重启会话身份与持久化细节留给实现章决定。

质量分类需覆盖有效、缺失、格式/范围无效、过期、重复、乱序和未知。重复或迟到消息可进入诊断/审计记录，但不得被当成新的当前测量；非法消息应拒绝接纳并产生可见原因。对新鲜度/乱序的时间窗口不指定固定秒数。

告警事件必须引用源事件 ID、规则 ID/版本、规则输入值/单位、触发时间、数据来源和可读解释。没有经批准的规则版本时，状态为未配置/未知，不设置默认阈值。规则参数变更应有批准、版本、理由、生效范围和回滚线索。

若章节展示 JSON，仅用明确的 `SYNTHETIC` 教学记录；它表达字段语义，不宣称已作为最终固件/RPC 序列化格式，也不包含真实传感器数值或现场阈值。

## 失效与恢复策略

| 条件 | 架构反应 | 禁止的错误表现 |
|---|---|---|
| 传感器缺失、非法或质量未知 | 记录原因；当前环境状态转为未知/数据异常，等待可判定的新事件 | 沿用旧值并显示正常 |
| Bridge/RPC 中断、超时或服务不可用 | 标记采集链路降级；在项目确认的新鲜度策略到期后显示未知；恢复后按事件 ID 处理重放 | 假设消息绝不丢失、无限阻塞或称 exactly-once |
| Linux 应用/进程重启 | 从本地记录恢复已保存历史；收到新的有效采集事件并确认规则/时钟状态前保持等待或未知 | 启动瞬间把缓存的旧状态当作当前状态 |
| 重复事件 | 依据稳定事件 ID 幂等接纳或去重，保留可审计计数，不重复制造新告警 | 将重复投递计为新采样 |
| 迟到/乱序事件 | 保留原始事件时间和诊断结果；按明确的排序/新鲜度策略处理，策略未定时不得静默覆盖当前状态 | 以到达先后代替测量先后 |
| 设备或主机时间不可信 | 保存可用的接收时间；将来源测量时间标记为未知/不可信；状态门禁使用显式健康标记 | 伪造准确 UTC 时间或用接收时间覆盖测量时间 |
| 本地持久化失败/空间不足 | 进入可见的存储退化/未知状态并保留诊断信息；队列容量及溢出策略在实现前单独决定 | 静默丢记录后继续报告无条件正常 |
| 规则缺失/未批准 | 显示未配置/未知并说明缺少规则版本 | 用教程样例值充当现场默认规则 |

本章不承诺 Bridge 重试语义、离线缓存容量或跨重启无损；其实现和目标板表现需后续测试证据确认。任何有界队列都需明确容量、溢出/恢复语义和可观察丢失计数，禁止无界增长。

## 章节交付与验证

获准实施后，章节应包含：

- 方案对比和推荐边界、组件职责、信任/网络边界；
- 一张唯一图号 Fig-61 的架构图，正文 Mermaid 与 `diagrams/` 源一致，并在 `images/第9篇_Project/README.md`、`images/README.md`、`diagrams/README.md` 登记；
- 版本化数据/告警契约及 `SYNTHETIC` 示例；
- Bridge 断连、进程重启、重复/乱序/未知时间、存储失败、规则未配置的失效矩阵；
- 离线架构走查实验、可判定预期结果、当前证据等级与后续验证门；
- SUMMARY、篇内导航和全书章节计数同步，保留 `draft` 状态。

离线测试检查章节结构、关键安全边界、图源一致、Fig-61 唯一、导航/本地链接和实测状态声明；同时仅在当前主机进程内执行正文中的无 I/O 纯函数，验证时钟可信度和持久化确认门禁（标记为 `HOST_TEST`）。测试不发起网络请求、不调用 Arduino CLI、不访问传感器/Bridge、不访问运行时数据文件、缓存或真实持久化后端，也不证明目标板兼容。完成后运行本章测试、相关全书测试、链接/图号/元数据静态检查及 `git diff --check`。Mermaid SVG 是否生成和目视检查另行标记，不由文本检查替代。

证据分级使用 `DESIGN_ONLY`、`SYNTHETIC`、`HOST_TEST`、`TARGET_OBSERVED` 和 `INDEPENDENT_REVIEW`。本章新架构为 `DESIGN_ONLY`；离线样例可为 `SYNTHETIC`/`HOST_TEST`。在另行批准并保留目标板、传感器、原始输出、版本和步骤证据前，UNO Q 实机状态为 `NOT_RUN`，不得标成 `TARGET_OBSERVED`。

## 未决决策（本章不得擅自填写）

- 要监测的物理量、器件型号、量程、精度依据、供电、电气域、接线、安装位置与校准。
- 每路采样周期、数据新鲜度/超时窗口、重试次数、批量发送频率与允许的传输延迟。
- 事件 ID 跨 MCU/Linux 重启的唯一性策略，以及确认/重放与缓冲/溢出语义。
- 时间源、同步策略、时钟不可信判断和重启后排序/去重策略。
- 本地存储技术、事务/日志模式、容量、留存期、备份/删除和空间耗尽处置。
- 告警阈值、滞回、去抖、规则审批者、通知方式和现场响应程序。
- 是否采用 Arduino App Lab 作为最终部署入口；其确切版本、启动恢复和发布流程。
- 任何远程遥测的目的地、数据字段、身份、权限、留存和退出审批。默认保持关闭。
- 目标板/传感器接入验证的授权步骤、观察方法、证据保存和停止条件。
