# 第八篇第 6 章规格：IoT 设备身份与安全通信

> 状态：规格已按用户指示确认；实施计划待审阅。｜日期：2026-09-24｜目标章节标题：IoT 设备身份与安全通信：从连接信任到最小权限

## 1. 目的与衔接

本章承接第八篇前五章，把之前刻意留在边界外的信任问题讲清楚：第 1 章定义遥测事件身份与数据契约；第 2、3 章说明 MQTT 传递、主题和离线补传；第 4 章观察运行状态；第 5 章建立受控命令和结果对账模型。第 5 章的请求主体是预先可信的教学输入，并未执行认证、凭据验证或 MQTT ACL。本章补充设备身份如何被建立并映射为授权主体、TLS 能保护什么、Broker 如何分别认证与授权，以及凭据如何轮换和撤销。

章节使用的安全策略是可读、可测试的教学策略，不宣称是普遍适用的产品配置、合规基线或认证要求。NIST IoT 能力目录把设备识别、数据保护、逻辑接口访问等列为需要按使用场景裁剪的能力；本书据此组织问题，不宣称符合 NIST 基线或联邦要求。参见 [NISTIR 8259A](https://csrc.nist.gov/pubs/ir/8259/a/final) 和 [NIST 技术能力目录](https://pages.nist.gov/IoT-Device-Cybersecurity-Requirement-Catalogs/technical/)。

4. 凭据登记、轮换、过期和撤销
5. 实验：离线检查合成设备安全配置

8. 常见误区、小结和延伸阅读

第 1 节用表格分清以下概念：`device_id` 是设备目录/应用使用的逻辑标识；`client_id` 是 MQTT 会话标识，必须由 Broker 按认证结果检查其可用性；`principal_id` 是可信认证组件或 Broker 得到的授权主体；`credential_ref` 只是指向秘密管理系统中凭据的非秘密引用；`correlation_id` 仅用于关联请求与结果。客户端自行在 JSON 载荷中声明的标识不能单独证明设备身份。

第 2 节说明 TLS 1.3 提供经认证的安全通道，可选认证客户端；协议本身是应用无关的，应用协议还需定义如何校验服务身份。客户端必须验证所连服务名与可信服务身份相符，不能用“连接已加密”代替服务身份校验。是否使用双向 TLS（mutual TLS，mTLS）是部署选择；客户端证书通过握手只表示某种客户端认证材料被使用，仍须由 Broker/认证层映射为受限主体。依据采用当前的 [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html)（2026 年 7 月更新 TLS 1.3 规范、取代 RFC 8446）及 [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html)；目标 TLS 库和硬件兼容性不在本章断言范围。

第 3 节依 [OASIS MQTT 5.0](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html) 区分客户端认证、客户端授权、发布/订阅资源权限和传输安全。明确 `Client ID`、用户名字段、主题名、`Correlation Data` 都不是凭空可信的身份凭证。教学 ACL 为 `default: deny`，只给当前设备授权精确主题：设备可向 `demo/v1/devices/{device_id}/telemetry` 发布，按需要向同一设备的 `state` 发布；设备只可订阅 `demo/v1/devices/{device_id}/commands`。规则拒绝跨设备路径和覆盖面过广的 `+`/`#`；这些是本章固定示例策略，不宣称所有部署都必须使用相同主题。

第 4 节解释唯一设备凭据、权限最小化、登记/安全下发、重叠窗口轮换、旧凭据撤销、过期拒绝与审计记录。生命周期演示仅使用元数据状态及虚构时钟，不生成或解析密钥、证书、Token，也不接入 Vault、CA、CRL、OCSP 或 Broker。必须避免共享设备秘密、把秘密写入仓库/日志、在服务端身份校验失败时退回明文，或将“轮换日期已填写”写成凭据已真正轮换。

## 4. 离线实验设计

### 目标

检查一份小型 JSON 教学安全配置是否符合本章自行定义的静态策略，并以具体问题代码解释拒绝原因。检查器不是认证器、TLS 客户端、证书解析器或 Broker ACL 测试器。

### 拟定输入模型

采用 Python 标准库可读取的 JSON，无真实秘密值。每个合成设备包含：

- `device_id`、`client_id`、`principal_id`：教学用稳定标识；
- `credential_ref`、`credential_type`、`credential_state`、`not_before`、`not_after`、`rotation_due_at`：非秘密生命周期元数据；
- `tls.enabled`、`tls.verify_server`、`tls.server_name`、`tls.trust_ref`、`tls.client_auth`：声明式连接设置；
- `authorization.default` 与 `authorization.rules`：默认行为及精确的 publish/subscribe 主题规则。

名称和结构在获批实施计划中可因静态测试需要微调，但必须保留“标识/认证/授权/通道/生命周期”之间的语义分离。输入中只出现虚构域名、虚构设备和无法使用的凭据引用；不得包含私钥、密码、有效令牌、可用证书或用户真实配置。

### 固定策略检查

检查器按命令行给定的合成参考时刻确定性执行下列检查：

- 必需字段、类型、枚举、日期顺序和设备/Client ID/principal 关联是否有效；
- 不同设备是否误用相同设备主体或共享身份；配置不能只凭 ID 字符串证明密钥属于该设备；
- TLS 是否声明启用、服务器身份校验是否开启，所需的服务名和信任引用是否存在；
- 授权默认是否为拒绝，允许规则是否限定于该设备主题及所声明动作，是否包含不允许的通配符/跨设备路径；
- 凭据是否在教学状态中已撤销、尚未生效、已过期或轮换日期已过；
- 输入是否意外包含命名为密码、Token、私钥等秘密字段或疑似内嵌秘密的值；诊断只报告字段路径和问题代码，不回显该值。

检查器输出机器可读的 JSON 结果及稳定问题代码，如 `TLS_SERVER_VERIFY_DISABLED`、`DEVICE_PRINCIPAL_REUSED`、`ACL_CROSS_DEVICE_TOPIC`、`ACL_WILDCARD_TOO_BROAD`、`CREDENTIAL_REVOKED`、`CREDENTIAL_EXPIRED`、`SECRET_LITERAL_REJECTED`。固定样例至少有一份通过配置，以及覆盖 TLS 校验关闭、共享身份、过宽 ACL、跨设备权限和无效/过期凭据的拒绝配置。所有时间来自显式传入的合成时刻；除读取指定输入外，检查过程不访问系统当前时间、网络、其他文件、外部服务或环境秘密。

最终 `PASS` 的精确定义仅为“输入符合本章固定的 JSON 结构和教学策略”。它不证明实际设备、证书、TLS 握手、主题 ACL、身份映射或生产安全成立。通过与拒绝样例都必须具有确定、可回归的输出；错误 JSON、未知字段、重复 JSON 键、超限输入或无效时间应安全拒绝，而不是静默忽略或放宽策略。
